MCP security checklist

Before you connect an agent to an MCP server, map the blast radius.

MCP is powerful because it gives agents tools. That is also the risk. This checklist helps you see what the agent can touch, what untrusted content can influence, and where ClawMoat-style policy gates belong.

The mistake: treating MCP security like prompt security.

Prompt injection matters, but it is not the whole boundary. Once an agent has an MCP server, the practical question is simpler: what can it do if it gets convinced to do the wrong thing?

For local agents, the answer can include terminal commands, repo edits, browser sessions, database access, Slack messages, credentials, memory, and outbound network calls. A safe model can still be attached to an unsafe tool surface.

1. Permission surface

Start with the tools the MCP server exposes. Ignore marketing labels and write down the actual host capabilities.

✓

List every tool and resource

Shell, filesystem, browser, network, database, auth, memory, clipboard, email, calendar, package manager, cloud APIs.

✓

Separate read, write, execute, and send

Reading a file is different from editing it. Opening a URL is different from sending data to it. Treat execution and outbound send as the highest risk surfaces.

!

Flag broad home-directory access

Access to `~`, browser profiles, `.ssh`, `.aws`, `.config`, shell history, and `.env` files should be explicit, narrow, and justified.

2. Untrusted input paths

Find the content that can influence the agent before it calls tools. Attackers do not need direct tool access if they can shape the instructions the agent reads.

✓

Mark every external text source

Web pages, GitHub READMEs, issues, docs, tickets, chat transcripts, email, PDFs, scraped pages, package metadata, logs, and tool output.

✓

Scan inbound tool results

Tool output should not flow straight into a privileged agent prompt without inspection. Treat tool output as data, not instructions.

!

Look for instruction smuggling

Comments, markdown blocks, HTML, encoded payloads, and “system” language inside external content are common places for hidden instructions.

3. Approval gates

The goal is not to block useful agents. The goal is to require friction at the dangerous edge.

✓

Gate destructive commands

Deletes, moves, chmod/chown, package installs, shell pipes, background processes, credential reads, and deploy commands should require approval or policy.

✓

Gate outbound data

Any action that sends file contents, tokens, repo data, screenshots, transcripts, or customer data off-machine needs an explicit allow rule.

✓

Log the decision

Record what was requested, why it was allowed or blocked, what content influenced it, and which policy matched.

4. Install and supply-chain path

MCP users often copy installation commands into the same environment where agents run. That makes install docs part of the security surface.

!

Avoid mutable pipe-to-shell as the primary path

`curl ... | bash` from a moving branch is convenient, but it trains users to execute remote code without inspection. Prefer package managers, release tags, checksums, or inspect-first instructions.

✓

Pin what can be pinned

Use release tags, package versions, checksums, signatures, and reproducible install paths where possible.

# safer pattern
curl -fsSL https://example.com/releases/v1.2.3/install.sh -o install.sh
less install.sh
sha256sum install.sh
bash install.sh

5. Minimal ClawMoat policy shape

Start strict, then add narrow exceptions. The policy should mirror the job the agent is actually doing.

# example policy posture
shell: require_approval
filesystem:
  allow_read: ["./repo"]
  deny_read: ["~/.ssh", "~/.aws", "**/.env", "~/Library/Application Support/*"]
network:
  allow_domains: ["api.github.com", "registry.npmjs.org"]
  block_unknown_outbound: true
browser:
  block_cookie_export: true
audit: full
