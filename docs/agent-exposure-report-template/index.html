Exposure report template

Stop saying “agent security.” Write down what the agent can actually touch.

Use this template to review AI agents, MCP servers, coding assistants, and local automation. It turns vague risk into a concrete exposure map: permissions, influence paths, approval gates, evidence, and fixes.

Use the templateRequest a free review

Why this exists

Most AI security discussions get stuck at the prompt layer. That misses the operational question that matters on a real machine.

If an agent is tricked, buggy, or overconfident, what can it read, run, modify, or send? This report format forces that answer into evidence.

  • Use it before connecting a new MCP server.
  • Use it before letting a coding agent touch production repos.
  • Use it before shipping agent features to users.
Good for

MCP servers, local coding agents, browser agents, workflow agents, internal copilots.

Not a compliance report

This is a practical exposure map. It is designed for engineering decisions, not checkbox theater.

Best output

One page of evidence, one risk table, one short fix plan.

1Scope

Name, repo URL, MCP server, assistant, or automation path.

YYYY-MM-DD, reviewer, scanner/version if used.

Local laptop, CI runner, dev server, production system, cloud workspace.

What the agent is supposed to do, and who or what it is allowed to trust.

Explicitly list what you did not inspect so nobody mistakes the report for a full audit.

2Permission surface

SurfaceCurrent accessRisk questionDefault gate
FilesystemRepo, workspace, home directory, config paths?Can it read secrets or modify source before review?Allow narrow repo reads. Gate writes and sensitive paths.
ShellCommands, package managers, background processes?Can it execute arbitrary code or install mutable dependencies?Require approval. Log command + reason.
BrowserCookies, logged-in apps, screenshots, downloads?Can it act as the user or extract session data?Gate authenticated actions and cookie/session access.
NetworkAllowed domains, webhooks, API calls?Can it send local data to unknown destinations?Block unknown outbound. Allowlist domains.
MemoryLong-term notes, vectors, summaries?Can untrusted content persist and influence future sessions?Review writes to durable memory.

3Influence paths

READMEs, issues, webpages, emails, PDFs, logs, package metadata, MCP tool output.

Where does tool output become prompt context? Is it labeled as data or treated as instruction?

Markdown comments, HTML, encoded strings, copied terminal output, fake system messages.

What exactly does the human see before approving a dangerous action?

Rule: if untrusted content can influence a tool call, the report should name the content path and the tool surface it can reach.

4Findings table

SeverityFindingEvidenceFix
HighAgent can read sensitive local paths while processing external docs.Tool policy allows broad filesystem reads. External README content enters the same context.Deny sensitive globs, narrow workspace, require approval for secret-like reads.
MediumMCP server exposes shell execution with no command class distinction.All commands flow through one generic tool. No separate gate for install, delete, deploy, or network send.Split command categories. Require approval for execute/send/destructive actions.
LowAudit log lacks input provenance.Logs show command and timestamp but not the content that influenced the action.Record source document/tool output IDs for reviewed actions.

5Minimal policy sketch

filesystem: allow_read: ["./repo", "./docs"] deny_read: ["**/.env", "~/.ssh/**", "~/.aws/**", "~/Library/Application Support/**"] require_approval_write: true shell: default: require_approval deny: ["credential export", "unknown pipe-to-shell", "destructive recursive delete"] network: allow_domains: ["api.github.com", "registry.npmjs.org"] block_unknown_outbound: true memory: require_review_for_writes: true audit: include_input_provenance: true

6Recommendation format

One change that reduces blast radius today without blocking normal work.

Policy or architecture change that needs engineering but not a redesign.

The one boundary decision maintainers must make explicitly.

Exact command, scenario, or workflow to rerun after the fix.
